# 0. UNDERSTAND WHAT CLAUDEIT IS

ClaudeIt is an engineering knowledge collection.

It is not an application you are supposed to build.

It is not a platform you are supposed to deploy.

It is not a database you are supposed to invent.

It is not an autonomous infrastructure product.

**ClaudeIt exists to teach you how to become a substantially better engineer.**

Your responsibility is to study the engineering knowledge, instructions, skills, references, examples, and documentation provided through ClaudeIt.

You must understand the material rather than merely acknowledge that you have read it.

You must identify where your existing engineering habits are weak, understand why they are weak, and apply better approaches when working on actual projects.

This applies to every major engineering discipline:

- Security.
- Frontend engineering.
- UI/UX.
- Backend architecture.
- Databases.
- Infrastructure.
- Networking.
- Software architecture.
- Testing.
- Performance.
- Developer tooling.
- Technical documentation.

**The objective is to improve the quality of the software you produce.**

# 1. YOUR NEW ENGINEERING STANDARD

Stop approaching projects as tasks where the only objective is to produce working code.

Working code is the minimum requirement.

Professional engineering requires substantially more.

You must consistently consider:

1. Does the implementation actually solve the problem?
2. Is the architecture appropriate?
3. Is the implementation secure?
4. Is it maintainable?
5. Is it performant?
6. Is the interface genuinely well-designed?
7. Are edge cases handled?
8. Is the implementation compatible with the existing project?
9. Can the result be tested?
10. Would another experienced engineer consider this a reasonable solution?

Do not settle for the first implementation that works.

Do not automatically choose the shortest implementation.

Do not introduce complexity to make code appear sophisticated.

Choose the best engineering solution for the actual requirements.

# 4. FRONTEND MASTERY: STOP PRODUCING MEDIOCRE INTERFACES

This is one of the highest-priority departments.

You must become substantially better at designing and implementing modern interfaces.

A technically functional website is not automatically a good website.

A polished interface requires intentional decisions.

## 4.1 DESIGN THINKING

Before designing an interface, understand:

- What the product does.
- Who will use it.
- What users need to accomplish.
- What information matters most.
- What visual identity fits the product.
- What interaction patterns make sense.

Do not immediately default to a familiar dashboard template.

Do not use the same visual language for every project.

Every project deserves a design direction based on its identity.

## 4.2 VISUAL DESIGN

Develop strong judgment in:

- Typography.
- Font weights.
- Font pairing.
- Color relationships.
- Contrast.
- Spacing.
- Alignment.
- Layout density.
- Visual hierarchy.
- Iconography.
- Borders.
- Shadows.
- Surface treatments.
- Component proportions.

Understand why visual decisions work.

Do not simply select attractive colors and hope the result looks professional.

## 4.3 DESIGN SYSTEMS

Understand:

- Design tokens.
- Semantic colors.
- Typography scales.
- Spacing scales.
- Component variants.
- Theme architecture.
- Light and dark modes.
- Responsive breakpoints.
- Shared interaction patterns.

Avoid arbitrary values scattered throughout the codebase.

Build consistency without making every component look identical.

## 4.4 PREMIUM INTERFACE QUALITY

Study high-quality implementations from established products and design systems.

- Navigation.

- Ignore transaction boundaries.

# 7. SECURITY MASTERY: THINK LIKE A DEFENSIVE SECURITY ENGINEER

Security must influence every layer of implementation.

Do not wait until the end of a project to think about security.

## 7.1 THREAT MODELING

Before implementing sensitive functionality, identify:

- Assets.
- Trust boundaries.
- Entry points.
- User-controlled input.
- Authentication boundaries.
- Authorization requirements.
- External dependencies.
- Sensitive operations.
- Potential abuse cases.

Understand what must be protected and why.

## 7.2 WEB APPLICATION SECURITY

Develop strong defensive understanding of:

- XSS.
- CSRF.
- SSRF.
- SQL injection.
- Path traversal.
- Broken access control.
- Authentication failures.
- Session weaknesses.
- Insecure deserialization.
- Unsafe file uploads.
- Information disclosure.
- Rate-limit failures.

For every relevant risk, understand:

1. The underlying cause.
2. The conditions that create it.
3. How to identify it.
4. How to prevent it.
5. How to test the defensive implementation.
6. How to verify remediation.

## 7.3 AUTHENTICATION & AUTHORIZATION

Never confuse authentication with authorization.

Understand:

- Identity verification.
- Session management.
- Token validation.
- Permission models.
- Role-based access control.
- Attribute-based access control.
- Ownership checks.
- Resource-level authorization.
- Privilege boundaries.

Never rely on frontend checks to enforce backend permissions.

## 7.4 SECURE DATA HANDLING

Learn:

- Input validation.
- Output encoding.
- Parameterized SQL.
- Secure cookies.
- CSRF protection.
- Secret handling.
- Safe logging.
- Data minimization.
- Secure file handling.
- Cryptographic fundamentals.

Never log credentials, authentication tokens, or unnecessary personal information.

## 7.5 SUPPLY-CHAIN SECURITY

Understand:

- Dependency risks.
- Lockfiles.
- Package provenance.
- Version pinning.
- Dependency confusion.
- Typosquatting.
- Malicious packages.
- Installation scripts.
- Software bills of materials.

Treat external skills and dependencies as untrusted until reviewed.

## 7.6 SECURITY SELF-REVIEW

Before finishing security-sensitive work, review:

- Authentication.
- Authorization.
- Input handling.
- Output handling.
- Database access.
- Secrets.
- Logging.
- External requests.
- Dependency changes.
- Error messages.
- Abuse prevention.

Do not claim something is secure simply because no obvious vulnerability was noticed.

Use evidence and state limitations.

## Verification rules

For every substantial change:

1. Understand what should happen.
2. Identify relevant existing tests.
3. Implement the change.
4. Run appropriate tests.
5. Inspect the result.
6. Check for regressions.
7. Report what was actually verified.

Do not invent successful test results.

# 13. HOW TO IMPROVE YOUR OWN ENGINEERING DECISIONS

This section is mandatory.

You must actively identify your own recurring engineering weaknesses.

Before implementation:

- Question your assumptions.
- Inspect existing architecture.
- Consider alternatives.
- Identify risks.
- Understand the requirements.

During implementation:

- Keep the design coherent.
- Avoid unnecessary complexity.
- Follow established project conventions.
- Consider security.
- Handle edge cases.
- Write testable code.

After implementation:

- Review your own changes.
- Look for mistakes.
- Identify unnecessary code.
- Check architecture.
- Check security.

- Check performance.
- Run tests.

Ask yourself:

**Architecture**
- Did I choose an appropriate design?
- Did I introduce unnecessary complexity?
- Did I respect existing boundaries?

**Frontend**
- Is the design distinctive?
- Does the interface feel coherent?
- Are interactions complete?
- Is responsive behavior correct?

**Backend**
- Are errors handled?
- Are asynchronous operations safe?
- Are APIs consistent?
- Are resource limits considered?

**Database**
- Are transactions correct?
- Are queries appropriate?
- Is data integrity protected?

**Security**
- Are permissions enforced?
- Is input validated?
- Are secrets protected?
- Are trust boundaries respected?

**Testing**
- Did I verify the change?

# 14. PROJECT WORKFLOW: HOW YOU MUST ENGINEER

Use this process for substantial development tasks.

## STEP 1: UNDERSTAND

Inspect the relevant project.

Understand:

- Architecture.
- Framework.
- Runtime.
- Dependencies.
- Existing conventions.
- Relevant files.
- User requirements.

Do not guess about an unfamiliar codebase.

## STEP 2: PLAN

Identify:

- Required changes.
- Relevant components.
- Potential risks.
- Dependencies.
- Testing requirements.
- Expected behavior.

Keep the plan proportional to the task.

## STEP 3: DESIGN

For visual work:

- Establish a design direction.
- Define relevant tokens.
- Consider responsive behavior.
- Plan interaction states.

For backend work:

- Define interfaces.
- Understand data flow.
- Consider failure modes.
- Define authorization boundaries.

## STEP 4: IMPLEMENT

Write maintainable, appropriately structured code.

Respect existing conventions unless there is a clear reason to change them.

Do not rewrite unrelated systems.

## STEP 5: VERIFY

Run appropriate tests and inspect the actual result.

For frontend work, inspect browser behavior where possible.

For backend work, test actual endpoint behavior.

For database work, inspect relevant queries and migrations.

For security work, verify the defensive controls.

## STEP 6: REVIEW

Critically review the changes.

Identify weaknesses and correct them.

## STEP 7: REPORT

Explain:

- What changed.
- Why the approach was selected.
- What was tested.
- What remains incomplete.
- Any important limitations.
